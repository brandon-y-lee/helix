# First production welcome email

## Customer outcome

A visitor can request a welcome email from the public footer, popup or email-preferences page. The visitor reads the same welcome-only wording at all three entry points, selects an unchecked consent box, receives a confirmation email and takes an explicit action to confirm. Only then may Helix send one welcome. An account, purchase, product waitlist entry or historical subscriber record grants no permission. A local withdrawal or delivery restriction recorded before an intent's irrevocable reservation prevents handoff. Withdrawal after reservation stops future handoffs, but one in-flight welcome can still arrive. Resend applies its global unsubscribe and Topic opt-out again when executing the Send Email step. Customers can withdraw without signing in. Auth and support email continue independently.

The existing production form, consent generations, sealed confirmation, local withdrawal, one-intent dispatcher, delivery budget and restrictive evidence are the starting point. The visible storefront currently submits to a different lifecycle handler. The existing production welcome also waits for a preexisting Contact. This proposal amends those two parts of [Spec #538](https://github.com/brandon-y-lee/helix/issues/538). No additional campaign, discount, customer import or administration UI is in scope.

## Provider delivery decision

Use the existing transactional sender for the ownership confirmation. For the confirmed welcome, use a dedicated Resend event with exactly one active Automation and one immediate Send Email step. Freeze the reviewed Welcome to Helix content as a published template, link it to the existing private Helix Marketing Updates Topic, and include the native preference placeholder. Resend creates a missing Contact when that event runs. Its Send Email step skips globally unsubscribed Contacts and explicit Topic opt-outs, including when the Topic defaults to subscribed. The topic default supplies no Helix consent. Existing Contact preferences are never overwritten. Resend adds both one-click headers when the template includes its unsubscribe placeholder. The mailbox's one-click action withdraws all Resend marketing, whereas Helix's existing local capability withdraws the Helix welcome. The native welcome carries the provider preference link. The confirmation retains the no-login Helix withdrawal link and all previously issued links keep working. Amend the original welcome-body contract to avoid putting Helix's bearer capabilities into event properties, provider run history or logs. The recipient can still withdraw in the welcome itself. A signed native global or pinned-Topic denial also applies withdrawal to that subscriber's existing Helix record. Show and test the effect through both systems. [Event API](https://resend.com/docs/api-reference/events/send-event) · [Native Send Email step](https://resend.com/docs/dashboard/automations/send-email)

The raw email endpoint leaves globally unsubscribed Contacts eligible when they have not opted out of its specific Topic. A subscriber-wide read key placed in the main site would also expose Auth and payment-related mailbox content. A native event lets the provider make both preference checks at send time. Resend's public OAuth scopes and API key types offer no event-only permission. Its event endpoint returns HTTP 202 and the event name, with no per-submission identifier or documented idempotency key. Every active matching Automation runs. [Global subscription behavior](https://resend.com/docs/dashboard/contacts/managing-unsubscribe-list) · [OAuth scopes](https://resend.com/docs/guides/building-a-resend-oauth-client) · [API keys](https://resend.com/docs/api-reference/api-keys/create-api-key) · [Idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys) · [Trigger behavior](https://resend.com/docs/dashboard/automations/trigger)

## Ticket sequence and acceptance tests

1. **Connect storefront signup to the existing production consent flow.** No native blockers. On the verified production host, render the welcome-only form and its readiness through the existing footer, popup and preferences entry. Use the existing production request body. Preserve the legacy flow on its retained host, including previously issued query and fragment links. Readiness covers effective runtime and stored enrollment plus the operator's qualification of the confirmation worker. When unavailable, display the paused state before the visitor submits. Verify scoped consent copy, keyboard use, mobile/desktop behavior, duplicate submission across surfaces, wrong-origin denial, unchanged old links, inert GET/HEAD and human-only confirmation. Local tests use the existing browser and disposable PostgreSQL harness.
2. **Send a single native welcome for a confirmed intent.** Depends on Ticket 1 and the reviewed integration of [#548](https://github.com/brandon-y-lee/helix/issues/548) for the cross-generation frequency limits. Route only the welcome through an isolated production worker. Its authenticated wakeup takes no email, event name, URL or message content from the caller. The worker resolves the canonical parent and deployment, claims one eligible intent itself, rechecks consent, suppression, generation, expiry and stored/runtime controls, and reserves existing frequency and quota limits atomically. Persist an immutable transport discriminator for each intent. Backfill existing rows to their original transport; create native welcomes only for new, explicitly confirmed generations. Make existing claim, prepare and retry functions exclude native intents even when called from an older binary, and separate the native worker's lease domain. The original confirmation worker still claims legacy confirmations/welcomes. A rollback stops the native wakeup and leaves native rows held until a compatible worker returns. Prove actual mixed-generation and mixed-version contention in PostgreSQL, with neither starvation nor entry into the legacy raw-send path. The externally callable site and its preview builds receive no provider management credential. The separate worker has independently controlled source, deployment and secret access. Its credential injector allows only the exact Resend event POST, fixed event name, validated destination from the leased row, no redirects and bounded payload. Treat the provider-side credential as account-wide even behind this restriction. Owner approval of its custody precedes provisioning.

   Commit an irrevocable single-attempt reservation before provider I/O. Bypass transport/SDK retries for this event. Concurrency, duplicate wakeups, process crashes and expired leases cannot claim it again. A failure before reservation remains retryable. A crash after reservation, timeout or lost 202 produces a durable hold and operator alert. A 202 records submission only. A matching native run can separately establish skipped/sent status, and bounded provider evidence can establish delivery. Correlate against independently verified immutable evidence; if the provider cannot establish a unique match, retain unknown. Preserve quota and do not send a replacement on ambiguity. Keep P1 confirmation retries idempotent under the existing mechanism. Use human-visible copy that describes the possibility of an already committed welcome after withdrawal.

   Exercise two simultaneous workers, withdrawal on either side of commitment, local suppression, duplicate or stale generations, clock/lease boundaries, missing Contact, existing global and Topic denies, contract drift, timeout and crash on either side of 202. Use the actual transactional SQL, HTTP stub of the documented API, a simulated provider global/Topic matrix, and fixed-destination transport tests. Record the possible single missed welcome after ambiguous failure. No production delivery guarantee follows from simulated provider tests.
3. **Rehearse the complete release and preserve withdrawal.** Depends on Tickets 1 and 2. Add an ordinary release-compatible database expansion for the three reviewed consent, delivery and event packages. Apply them in order, starting empty and disabled, and include any reviewed changes from #548. Exercise the scheduled worker and cleanup cadence with isolated inputs. Bind source, exact deployment/parent, one effective Automation/Topic/template/approved From and Reply-To, user-visible postal address, and a quota with headroom for transactional and inbound traffic. Verify quotas for both contacts and automation runs without enabling overage billing. Use a dedicated sender reserved for this welcome and independently confirm its exclusivity. The suggested sender is welcome@helixskin.us and the checked existing shared inbox is support@helixskin.us for Reply-To. On verified account-wide contact.updated or contact.topics.updated, normalize and restrict only an existing Helix subscriber on an explicit global deny or denial for the pinned Topic. Never create or reactivate a subscriber from a callback. On a signed bounce, complaint or suppression from the reserved sender with one independently bound existing marketing recipient, persist an address-level restriction across generations without claiming delivery of any particular intent. Keep Auth, support and payment senders outside this handler. For any credible native restrictive event lacking a safe unique recipient, conflicting sender ownership, or unprocessable native denial, durably hold native dispatch for reconciliation. Positive delivery remains unknown without an immutable match. Verify duplicate/out-of-order and withdrawal-before/after cases, wrong signatures, wrong topics, same-recipient Auth/support fixtures, mixed ownership, global and single-Topic opt-outs, and the owner-facing indication of holds. Verify drift pause, shared webhook continuity and authenticated operator reconciliation. If the current account-wide callback requires a routing change, establish [legacy continuity](https://github.com/brandon-y-lee/helix/issues/555) before that action. Route changes have their own authority. Confirm the qualified current release workflow at that stage, including the outcome of [#587](https://github.com/brandon-y-lee/helix/issues/587), and keep held historical releases held.

   Before public enrollment, deploy the approved code with enrollment and dispatch off. Verify protected or recipient-gated canonical testing under the actual host, deployment and scoped controls. Use synthetic addresses locally. Any hosted mailbox rehearsal requires explicit recipient and send-count authority plus actual delivery/preference evidence. Pause dispatch first, then enrollment, and leave withdrawal and restrictive event processing operational. Reconcile prepared/in-flight reservations before resuming. Preserve historical evidence through application rollback.
