## 1. Customer outcome and completion boundary

A visitor or signed-in customer can add Super Serum 30 mL at its existing $25 price, pay through clearly identified Stripe-hosted Sandbox Checkout, and see accurate private Order status. Stripe delivery and recovery run on hosted infrastructure with no laptop listener or local RPC service. A Sandbox Order never causes a real charge, shipment, customer email, review invitation, or transferable live rewards.

S1 closes only after its code is integrated into dev and a separately recorded, freshly verified non-production operational activation proves the complete hosted journey. Each child Ticket closes on its reviewed source/tooling acceptance and Ticket merge. S1-05 supplies the guarded operational commands and runbook; the sole Spec Closer executes the approved bounded non-production activation against the final merged dev SHA, then records its evidence and closes the Spec issue. No source edits occur after merge outside a new reviewed Ticket. The Spec remains open with a precise operational blocker if activation cannot complete; a source merge alone is not evidence that Super Serum is available or hosted checkout works.

The production follow-on is S2. It has its own Spec boundary so outstanding live work cannot hold S1 off dev. No S1 code accepts live keys/objects or changes the sandbox-only database environment enum.

## 3. Checkout admission and existing-payment settlement

Split the current configuration seam into validated sandbox provider configuration and a separate admission decision. `CHECKOUT_ENABLED=false` prevents creation/replacement of Sessions but does not block signature verification, inbox receipt, processing previously accepted Sessions, owned status views, expiration or refund recording. Missing/invalid provider credentials still fail closed. Do not silently substitute a different key, environment, account or origin.

Checkout POST and cancellation POST require same-origin requests against the exact configured staging/local-loopback origin. Reject missing, null, malformed or unapproved Origin for browser mutation endpoints. Stripe webhook and credential-authenticated worker endpoints use their own authentication, not browser-origin enforcement. Validate strict JSON objects, supported reward input and actual streamed body length before parsing; cap checkout/cancel JSON at 4 KiB and webhook raw body at 1 MiB. Return bounded 400/403/413/429/503 errors without provider details or PII.

Use a shared database-backed admission limiter keyed by authenticated user or hashed guest ownership, with at most five new provider attempts per minute per identity and at most one active attempt per cart generation. Legitimate replay of the existing same logical attempt returns the existing result and consumes no additional provider-create quota. Add a shared aggregate budget of 10 new provider attempts per minute per Helix Stripe account/environment for S1, so rotating guest cookies cannot reset all limits. Coalesce concurrent owned status/replay provider lookups with a five-second per-Session/attempt cooldown and a separate shared 30-refreshes-per-minute account/environment budget; return already-authorized stored state with truthful pending/retry information when refresh is deferred. Existing same-attempt replay avoids create quota but does not bypass these provider-read controls. Worker/webhook settlement has separate capacity and cannot be starved by browser create/refresh quotas. Test rotating guest cookies and concurrent status/replay requests. These are conservative sandbox budgets; S2 must set measured live capacity. Keep trusted-edge/IP limits optional defense in depth; never rely on attacker-provided forwarded headers or an in-memory counter as the primary limiter. When shared limit/authorization storage is unavailable, creation fails closed and existing settlement remains available.

Set `payment_method_types: ["card"]` on new Sessions and save truthful method-policy metadata. Preserve server-authoritative prices, integer cents, immutable line snapshots, quantity bounds and established cart-generation/attempt/session compare-and-swap rules. Never derive price, discounts, ownership or rewards eligibility from browser input. Reject a zero-total quote with a clear unsupported-checkout message before creating a Session in S1; handle any legacy `no_payment_required` Session as a durable operator exception, not paid or permanently spinning.

## 4. Private and truthful order status

Authorize access before provider retrieval, reconciliation or rendering. A signed-in Order requires the current server-authenticated owning user. A Session ID alone is never receipt authorization.

For guest Orders, issue a 32-byte random checkout-receipt capability in a Secure (hosted), HttpOnly, SameSite=Lax host-only cookie with Path=`/` (no Domain attribute), so both `/api/checkout/sessions` and `/checkout/success` receive it; store only its hash bound to that guest Order and environment. Capability lifetime is 24 hours from creation and cannot be extended by presenting a Session ID. Issue and bind the capability before returning any payable Session URL; a later creation request can reuse the same browser capability without changing access to an earlier Order. Test two guest checkouts in separate tabs and later refresh of each, including actual browser cookie-path behavior. The capability is independent of cart and cancellation cookies so clearing, editing or merging a cart does not erase the receipt immediately. Use one browser capability with explicit per-Order grants in the database and indexed lookup, rotated when expired; do not store an unbounded list in cookies. The shared admission limits bound grant creation; expired grants can be retired without deleting financial history. Do not use this capability to read signed-in Orders. Ownership changes invalidate superseded guest grants; login does not let one account claim another guest Order without its established ownership proof.

Use a private, non-cacheable response for success/status, with no sensitive metadata and a restrictive referrer policy so Session IDs are not sent to third-party destinations. Unknown, expired or unauthorized requests receive the same neutral unavailable response. Logged-in customers retain Order access through their existing account pages; guest receipt expiry does not authorize building an email-based recovery system in S1.

Headings, document title and accessible labels agree with state: awaiting payment/processing, verified sandbox payment, failed, cancelled, refunded, or unable to verify. Missing browser return never prevents settlement. A bounded status refresh polls only after authorization, backs off and stops on terminal status, tab invisibility or a time limit; manual refresh remains safe. No side effects originate from UI optimism.

## 5. Payment verification and addresses

Read canonical accepted Order lines and the authenticated provider Session, expanded or retrieved with authoritative line items and PaymentIntent where needed. Before paid finalization verify environment, expected account context, stored Session-to-Order relationship, order/attempt metadata, USD currency, whole-number nonnegative monetary fields, exact line identities/quantities/unit amounts and merchandise subtotal, selected coupon economics/discount and shipping amount, and total arithmetic including provider-computed tax. Persist the original quoted facts separately from the verified tax/final-total result; never infer missing monetary fields from old totals to mark paid.

Tax changes are permitted only under the Session's recorded automatic-tax contract. When automatic tax is enabled, require completed calculation and preserve its validated breakdown; add `customer_update.shipping: "auto"` for returning Customers when collecting shipping. Use `session.collected_information.shipping_details` for shipping recipient/address and `customer_details.address` for billing. Require usable US physical-delivery data before a paid Order becomes eligible for downstream work. A provider-confirmed payment with invalid address or quote enters a durable exception; do not deny that money may have been paid or manufacture a valid address.

Verification mismatches do not clear carts, award benefits or claim completed checkout. Record a sanitized exception code and IDs for the operator, retain the provider payment reference, and allow explicit repaired reconciliation. A delayed failure cannot downgrade a verified paid/refunded state. Existing atomic finalization and idempotent cart/reward operations remain the source of truth; add tests at these boundaries rather than duplicating business rules in the worker.

### Compatibility for previously accepted Sessions

New accepted attempts record a new verification schema version; persist the version on the local Order/Attempt before provider creation. Select validation from this trusted local version, never from incoming event metadata alone. Preserve a bounded `checkout_v1` path only for genuinely pre-cutover local Orders/Attempts: prove existing recorded Session ownership (or recover the original binding from trusted order/session references), immutable local line/subtotal/discount/shipping facts, sandbox account/mode, provider Session tax configuration and current payment state. Missing a new attempt ID or tax snapshot on a legacy row is not itself a reason to strand it. Do not reconstruct legacy accepted terms from today's cart/catalog/coupon configuration. If historical facts cannot establish the relationship or economics, retain an explicit operator exception with the actual provider payment reference; never weaken new-version checks or manufacture a missing snapshot.

Test pre-cutover paid, unpaid, expired and delayed-method Sessions with no new fields through webhook and owner status retrieval. Legacy guest status requires provable existing guest/cart ownership; issue a new receipt grant only after that proof. Missing guest proof makes the private view unavailable without preventing trusted background settlement. Migration preserves processed-event deduplication and treats legacy unfinished markers as recoverable work rather than erasing history.

## 6. Durable webhook receipt and recovery

Use an additive extension of the existing event audit or a new logged inbox table, with unique `(account_id, environment, event_id)`, verified event type/object ID/API version, receipt time, state, attempts, next-attempt time, lease token/expiry, processed time and sanitized failure category. Preserve existing processed records and replay idempotency. Store the minimum verified envelope only; no raw provider payload, addresses, full emails or secrets.

The webhook verifies the unchanged raw body using the existing hosted endpoint signing secret and sandbox mode guard, persists durable receipt, then returns 2xx. A duplicate may return 2xx only when its original work is durably queued or complete. If receipt cannot commit, return retryable non-2xx. Never treat a fresh processing marker as proof of completion. No unawaited background promise is responsible for processing.

The worker fetches current trusted provider state using the envelope, binds it to the recorded order/attempt, and drives the same reconciliation service used by authorized customer refresh. Supported Helix events that arrive before Session attachment or PaymentIntent mapping remain retryable. Unrelated provider events can become ignored only after trustworthy evidence establishes no Helix ownership; absence of a local row alone is insufficient. Keep older asynchronous sandbox Sessions settleable although new Sessions are card-only.

Processed/error writes require the current lease token. Stale workers cannot complete or reset a newer claim. Payment/order/reward mutations also recheck current state under transaction/uniqueness boundaries so duplicate event IDs, separate events describing one Session, worker overlap and customer refresh cannot duplicate effects. DB operation errors are checked. A full-refund path that cannot complete reward reversal stays an explicit operator exception and never marked fully reconciled. Add `refund.created`, `refund.updated` and `refund.failed` to the existing five-event sandbox endpoint subscription without changing its identity/API version or rotating its signing secret. The worker records/retrieves minimal refund facts (Refund/Charge/PaymentIntent IDs, currency, amount, current status) and links them to the Order. Partial/pending/failed refunds are durably visible for review; only authoritative successful refund amounts can support returned-money status, and a fully successful refund can use the existing path only when every local effect completes. They are not silently reported as complete financial support; full live refund accounting belongs to S2.

### Hosted worker and operations

- Scheduler: Supabase Cron (`pg_cron`) plus `pg_net` calls `POST /api/internal/payments/reconcile` every minute. The logged inbox is the durable store; the HTTP wakeup queue is not. Use no new paid scheduler. Official [Cron](https://supabase.com/docs/guides/cron) and [pg_net](https://supabase.com/docs/guides/database/extensions/pg_net) support this pattern.
- Fresh read-only inventory on 2026-09-18 found `pg_net` 0.20.3 and Vault 0.3.1 installed; `pg_cron` 1.6.4 is available but not installed. S1 proposes an additive enablement migration and one specifically named job after capability/capacity checks. Never alter unrelated jobs, extension settings or versions. The activation Ticket must include this exact change in its approved manifest.
- The wakeup credential is dedicated, high-entropy, server-only, stored in Supabase Vault and Vercel sensitive configuration; it is not a public Supabase key or service-role key. Constant-time credential comparison, POST-only, 1 KiB body bound, no arbitrary target URL or object ID in the request, no body/credential logging. The worker derives its account/project/origin from verified server configuration. Restrict Vault and internal wrapper function grants; inspect/restrict access to credential-bearing pg_net queue rows and Cron job definitions/logs, and never embed the credential literal in the scheduled SQL. Read it from Vault inside the narrow wrapper. Verify anon/authenticated/catalog-only roles cannot read it through any of these surfaces; do not expose it through an RPC.
- Each invocation performs at most 20 due work items and runs for at most 40 seconds within a verified 60-second-or-greater function limit; individual provider calls have bounded timeouts. Claim only work that can fit the remaining budget. Use 90-second leases and row locks/skip-locked claiming. Configure `pg_net` HTTP timeout to exceed the worker budget, and let a dropped wakeup recover at the next schedule. Platform runtime incompatibility blocks activation instead of silently reducing recovery guarantees.
- Retry delay: 1, 2, 4, 8, 16, 32 then 60 minutes capped, with bounded jitter; respect provider Retry-After when longer. At most 12 automatic processing attempts; schema/authorization/mode/quote mismatches quarantine immediately. A worker crash counts as an attempt, and expired leases are recoverable.
- Persist an incident for work pending more than 15 minutes, exhausted retries, any unknown provider outcome or financial mismatch; expose queue depth/oldest age and heartbeat through a minimal `/admin/payments` operations view under a new `payments.manage` capability granted only to the existing admin role, plus a read-only `payments:plan` command. Heartbeat older than five minutes is unhealthy even if Cron says the HTTP request was queued. The authorized maintainer operating the rehearsal checks this every five minutes and before/after each run. S1 does not pretend a passive dashboard or command provides unattended paging; S2 must connect an approved notification channel and responsible on-call operator before live launch.
- Provide authenticated, audited replay by exact quarantined item with expected version/reason, bounded batches and default dry-run. Replay resets eligibility only, never rewrites payment facts. Store actor identity and reason; ordinary customers/catalog-only roles cannot inspect the inbox or invoke replay. Secrets are never command-line arguments or printed evidence.

The existing `catalog_publisher` capability list currently aliases all admin capabilities. Replace that broad inheritance with the explicit existing catalog capability set before adding `payments.manage`; admin alone receives payments access. Test catalog_editor, catalog_publisher, ordinary authenticated and anon denial, plus active admin success.

New inbox/attempt/receipt/limit/incident data and internal functions require RLS, narrow grants, safe fixed search_path for necessary security-definer functions, and explicit anon/authenticated denial tests. Customer access is through authorized server routes only; preserve existing owning-customer Order reads.

## 7. Unknown outbound request outcome

Before requesting a Session, persist a logical attempt with immutable accepted request fingerprint, first-send timestamp, idempotency key, schema/API version and state (`prepared`, `requesting`, `attached`, `unknown`, terminal/quarantined). Reuse identical request parameters for retries of that attempt; never rebuild from a changed cart under the same key.

A network timeout or failed local attachment after provider creation is unknown, not definitely failed. After an unknown result, reconcile trusted provider Sessions/events using the attempt/order references before replacement. Permit idempotent request retries only within a conservative 23-hour window from the first send, with the identical request. Beyond that window, do not create again under either the old key or a new key until there is conclusive proof the prior operation cannot still be paid. If lookup is inconclusive, quarantine and retain reservations for explicit recovery, with truthful UI. The operator must resolve those reservations; do not silently release them while a payment may still succeed. Known Session expiry/status can provide proof, but search eventual consistency or absence from one page cannot.

Test with a controllable clock: provider creates then response is lost, DB attachment fails, webhook arrives before mapping, webhook never arrives, process crashes, cart changes, retry beyond 24 hours, and later authoritative discovery. Assert at most one payable purchase intent per logical attempt, one accepted Order outcome, no double benefits and no unnoticed reservation leakage. [Stripe idempotency retention](https://docs.stripe.com/api/idempotent_requests)
