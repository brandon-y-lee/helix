# Restricted welcome subscriptions

Ticket #436 / Spec #430 supplies source and local verification. It does not create provider resources, change hosted configuration, apply a remote migration, enroll a real Contact, or send email. R1-10 owns the exact activation manifest and hosted proof. Consent and welcome messages use the shared delivery service with its existing Order and Support safeguards.

## Ownership and native reuse

Resend owns Contact records, the welcome Topic, template authoring, and delivery. Helix owns affirmative consent evidence, confirmation, withdrawal, the current subscription generation, and eligibility at each provider handoff. A Contact, import, Account, Order, or Product Waitlist Enrollment cannot grant Marketing Consent.

Use a dedicated welcome Topic whose immutable default subscription is **Opt-in**. This default never supplies consent: only Helix’s current confirmed generation may pass the delivery guard. Native Broadcasts and Automations using this Topic remain disabled. Resend also exposes global Contact unsubscribe state; global withdrawal overrides Topic opt-in. Verify the actual Topic's default before activation rather than relying on its name. [Resend Topics](https://resend.com/docs/dashboard/topics/introduction)

Native Automations document skipping remaining email steps after global unsubscribe. Stopping an Automation prevents new runs while existing runs finish. Those guarantees do not establish this release's atomic cap across subscription generations, exact Topic checks, or retry-safe event admission. This implementation therefore uses only the three fixed purposes below through Helix's existing delivery service; it does not emit native Automation events. Native campaign authoring remains in Resend. Broadcasts and other promotional sends remain disabled until they participate in the same cap. [Automation runs](https://resend.com/docs/dashboard/automations/runs), [email idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys)

## Consent and fixed delivery contract

The public `/email-preferences` page requires an unchecked consent choice and a separate confirmation action. Opening a link never changes consent. The confirmation capability expires after 24 hours; a repeated pending request rotates it. Confirming an already-consumed valid token cannot start another generation. Requests for an already-confirmed address do not restart the welcome series. A new explicit request after withdrawal creates a new generation that must be confirmed again.

| Purpose | Eligibility and timing |
| --- | --- |
| `marketing_confirmation` | A fresh, explicitly consented request; a necessary address-confirmation message, separate from the promotional cap. |
| `welcome_initial` | Once for the current confirmed generation, due at confirmation. |
| `welcome_education` | Once for that generation, due 72 hours after confirmation, after the initial welcome was accepted. |

Promotional eligibility requires current local consent, a completed current-generation Contact sync, and fresh global and Topic preference evidence bound to the same Contact, Topic, generation, and revision. Unknown provider state defers delivery. A provider withdrawal makes local eligibility restrictive; provider opt-in cannot independently grant it. Provider mutations use revision and lease checks; an obsolete completion repairs toward current preferences. Helix never writes global opt-in or Topic opt-in to an existing Contact. A fresh confirmation does not clear an existing native unsubscribe; that preference must be changed independently by the customer before another confirmation can become eligible.

For an absent, unbound Contact, synchronization submits one fixed, in-memory CSV row with explicit `email`/`unsubscribed` mapping, literal `false`, and `on_conflict=skip`. It omits Topic, Segment, and custom-property fields. Resend documents that skip leaves existing Contacts untouched; the normal create/upsert path is not used. Helix verifies the Topic’s default before admission. [Import behavior](https://www.resend.com/changelog/csv-contacts-import), [Import API](https://resend.com/docs/api-reference/contacts/create-contact-import)

A durable per-address import admission is recorded before submission. Only its inserting transaction may submit; a lost response is unresolved, never blindly replayed. Known imports are polled to terminal status across withdrawals and welcome expiry. Completion only queues current preference synchronization; it cannot grant consent or revive the initiating generation. Welcome handoff remains blocked while any import is unresolved. Unknown-ID work continues to queue restrictive repair if a late Contact appears and needs operator reconciliation. A completed one-row import must report total 1, updated 0, failed 0, and created plus skipped 1; fresh Contact/Topic reads still decide eligibility.

The first import failure retains only an allowlisted category, HTTP status, error name, and bounded retry delay. Rate limits, configuration rejection, and ambiguous failures remain distinguishable without storing raw provider messages. Only the exact `429 rate_limit_exceeded` pair may schedule a bounded retry of the same skip-only request, after its rejection and delay have been durably recorded. This is an engineering inference from Resend's documented HTTP rate-rejection and follow-up contract, not a claimed endpoint transaction guarantee. Each attempt rechecks restricted recipient, current confirmed consent, current native Contact, and Topic configuration. Concurrent workers cannot share submission authority; at most three attempts occur within one hour, with no worker sleeping through backoff. [Error reference](https://resend.com/docs/api-reference/errors), [API rate limits](https://resend.com/docs/api-reference/rate-limit)

Timeouts, malformed or mismatched failures, `5xx`, and lost successful import identities stay unresolved and are never automatically replayed. Failed persistence of a rate rejection cannot authorize another attempt. Correcting configuration or observing a Contact cannot prove an earlier import is finished; approximate timestamp/count matching is not identity evidence. The read-only `pnpm email:deliveries marketing-status` command exposes finite diagnostic states and remediation guidance without addresses, message content, or tokens. R1-10 must qualify a deliberate operator reconciliation procedure before activation; the source provides no unknown-ID rebinding, reset, or replay escape.

Imports deduplicate case-sensitively. Before activation, qualify the canonical-address namespace—including allowed development recipients—and reject unresolved mixed-case variants. Established Contact IDs remain bound; a missing bound Contact cannot be recreated automatically. No deletion/import cleanup may erase native opt-out history. [Resend migration guidance](https://resend.com/migrate/mailchimp)

The shared preparation transaction enforces no more than one promotional handoff per normalized address in a rolling 24 hours and three in seven days, including across generations. First handoff reserves capacity; retries reuse that reservation and advance its latest possible handoff time. Accepted or uncertain handoffs remain charged, including a late retry near the end of the reconciliation window. An unattempted welcome expires 24 hours after its due time, preventing a delayed backlog. An attempted message retains the existing frozen request, stable key, bounded attempts, and conservative 23-hour reconciliation window. Expiring an unattempted welcome never relabels an uncertain send as unsent. The local PostgreSQL harness covers overlapping transactions alongside the existing Order and Support contracts.

Preference capabilities can withdraw either welcome messages or all promotional messages. They cannot grant consent, expose an address, or grant Account access. An older preference link still withdraws the current subscription. Welcome-only withdrawal does not globally resubscribe a Contact. The one-click endpoint accepts the bounded `List-Unsubscribe=One-Click` POST and withdraws all promotional messages. A local withdrawal commits before any later preparation can pass. A native preference change can race the short interval between the final provider read and an already-starting handoff; no Helix write restores that preference. A message already handed to the provider may arrive. Confirmation and withdrawal remain usable when `HELIX_MARKETING_ENABLED` pauses new requests.

## Immutable template approval

The private `HELIX_EMAIL_MARKETING_CONTRACT` JSON has exactly these top-level fields: `version` (`welcome_v1`), `siteOrigin`, `from`, `replyTo`, `postalAddress`, `topicId`, and `templates`. The last field contains exactly `marketing_confirmation`, `welcome_initial`, and `welcome_education`, each with a native template UUID `id` and lowercase SHA-256 `sha256`. Every generation retains its approved contract.

Approve a published native template with no unpublished versions. `marketingTemplateFingerprint` in `lib/marketing/templates.ts` validates the native response and hashes UTF-8 `JSON.stringify` output with fields in this exact order: `id`, `version` (the native `current_version_id`), `subject`, `html`, `text`, `from`, `replyTo` (native `reply_to`). Preserve exact content, nulls, and array order; a hash of HTML alone is insufficient. A new publication or content change requires a new approval. Native sender and Reply-To, when populated, must match the contract. [Retrieve Template](https://resend.com/docs/api-reference/templates/get-template)

Only `HELIX_SITE_ORIGIN`, `HELIX_POSTAL_ADDRESS`, and the purpose's link variable may be substituted using double or triple braces. Confirmation requires `HELIX_CONFIRM_URL` in both HTML and plaintext. Each welcome requires `HELIX_PREFERENCES_URL` and `HELIX_POSTAL_ADDRESS` in both formats. Unknown variables or changed template content fail closed. Promotional requests include the exact Topic and one-click unsubscribe headers. The first attempted request freezes rendered bodies and links; it does not defer rendering to a mutable native template ID.

The outgoing `topic_id` field is supported by Resend's official Node SDK: its `topicId` email option maps to `topic_id` for `/emails`. The public Send Email page may omit it, so the pinned SDK contract supplies the wire evidence. Helix still enforces current Topic preference and frequency limits before each handoff; this field is not treated as proof of atomic provider-side consent enforcement. [SDK email options](https://github.com/resend/resend-node/blob/v6.30.0/src/emails/interfaces/create-email-options.interface.ts), [SDK wire mapping](https://github.com/resend/resend-node/blob/v6.30.0/src/common/utils/parse-email-to-api-options.ts)

Use `https://helixskin.vercel.app` only as the development web origin. Sending identity, Reply-To, postal address, and Topic are separately approved. An owned domain change applies to future approved contracts; keep previous link and reply routing usable for pending messages. Do not rewrite an attempted envelope.

The service-only `read_marketing_email_control()` reads the three purpose controls. `configure_marketing_email(p_enabled, p_expected_updated_at)` changes all three atomically using the inspected map of purpose to `updatedAt`. Enabling establishes a fresh acceptance cutoff; it does not backfill historical consent or revive old welcome generations. R1-10 owns any actual activation.

Only the verified Resend account owner and explicitly enabled official simulator addresses may be used in development. Rejected recipients receive no redirected email. Simulator events prove event handling, not receipt in a human mailbox.

The hosted rehearsal must prove confirmation and scanner-safe links; repeated requests and confirmation; fresh and stale global/Topic withdrawal; withdrawal during import submission/completion, synchronization, first preparation, and retry; skip-mode imports preserving existing global/Topic denies; ambiguous import outcomes staying blocked; rapid withdrawal/reconfirmation across generations; concurrent cap competition; expired unattempted work; unavailable provider reads; immutable template rejection; and frozen-request recovery after uncertain acceptance. Verify desktop/mobile email and plaintext, meaningful links, postal address, and one-click unsubscribe. Preserve only sanitized identities, timestamps, SHA, and outcomes in evidence; do not record addresses, tokens, message bodies, secrets, or raw provider errors.

The private `GET` or `POST /api/internal/marketing-sync` worker uses the existing `HELIX_EMAIL_DISPATCH_SECRET` and requires `HELIX_MARKETING_SYNC_ENABLED=true`. It reconciles at most one import job and one preference job per invocation, with three-second bounds for each complete provider operation and database response. Topic reads have one three-second deadline and a maximum of five pages. Shared email dispatch claims one intent; its complete provider send is bounded to eight seconds, yielding a maximum welcome I/O budget of approximately 32 seconds. Both routes stay within their 60-second limit, including error recording. The restricted cadence and throughput must be qualified before general customer delivery.

The preference worker is separate from email delivery so `HELIX_MARKETING_ENABLED=false` can pause new subscriptions and `HELIX_EMAIL_DISPATCH_ENABLED=false` can pause sends while withdrawal repair and import polling continue. Keep the sync worker enabled for outstanding work, and preserve signed delivery reconciliation. R1-10 must register and prove both worker schedules; the source adds no hosted cron configuration. Do not delete consent evidence or logical message identities to retry or reset a generation. The shared delivery recovery and disable contract is documented in [Order confirmations](./resend-order-confirmation.md).
