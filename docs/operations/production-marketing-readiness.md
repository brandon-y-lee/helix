# First production welcome email

The footer, popup and email preferences page request one welcome email. A visitor checks the consent box, receives an ownership confirmation from `hello@helixskin.us`, then confirms on the website. A link scanner opening the confirmation URL cannot subscribe anyone. The next eligible worker run sends one welcome from the same address. Replies reach the monitored hello inbox. Each message includes a visible first-party withdrawal link. The welcome also supplies RFC 8058 one-click headers and the Helix Marketing Updates Topic.

Held Production builds show customers the paused form. Only the canonical serving site accepts enrollment. Auth mail, customer support and historical preference links keep their original destinations. Existing Contacts, purchases, Accounts and legacy subscribers never enter this welcome automatically.

## Stage and activate

1. Follow the [database package instructions](../../supabase/operations/production-marketing/README.md) for the actual target. The normal protected migration after the two Catalog and four Checkout entries is `20261121090054`. It installs a paused production store or adopts the development child's existing consent state. The approved owner enrollment can replace the specifically verified unused earlier installer. An unexpected schema or ledger stops the release. Existing withdrawal capabilities continue to work.
2. Review the footer, popup and `/email-preferences` on the exact held Production URL. `GET /api/marketing/production/subscription` returns `{"production":true,"enabled":false}`. Reviewers can test the complete journey with the local synthetic proof below while customer enrollment is closed.
3. Configure Production once. Set `HELIX_PRODUCTION_MARKETING_SITE_ORIGIN` to `https://www.helixskin.us`, the production Supabase URL and Vercel project ID in their corresponding marketing target settings. The server uses the existing parent-bound `SUPABASE_SERVICE_ROLE_KEY` and public project binding. Keep `HELIX_PRODUCTION_MARKETING_PROVIDER_KEY` scoped to sending from `helixskin.us`. The server needs distinct abuse, capability, worker and webhook secrets and a capability key ID. Set the storefront's `CRON_SECRET` to an independent 32–256 printable-character value. All secrets stay in the Production environment. The public sending contract is defined in `lib/production-marketing/delivery-config.ts`. The compiled default sets both From and Reply-To to `hello@helixskin.us`, the approved Helix Labs LLC postal address, reviewed template and Topic `aca091c7-8da7-440e-8761-e6a549c60aa5`.
4. On the approved callback cutover, use the account's single webhook at `https://www.helixskin.us/api/webhooks/marketing-production`. Subscribe to `contact.created`, `contact.updated`, `contact.topics.updated`, and the seven outgoing states `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.failed`, `email.bounced`, `email.complained` and `email.suppressed`. Use Resend’s endpoint signing-secret rotation and store only the newly returned signer in Production-only `HELIX_PRODUCTION_MARKETING_WEBHOOK_SECRET`. The dedicated receiver accepts that new signer alone. Resend can deliver a previous and current signature during its rotation grace period; keep both signing keys out of development changes and verify the old key expires. A URL edit by itself leaves key custody unchanged. Account for the interval between the endpoint destination switch and verified reception at the canonical site. Keep enrollment and dispatch closed while building with the new signer, verifying delivery of signed intake, and taking the complete preference baseline. Retiring the old demo callback ends future legacy delivery receipts and app-created support tickets on that callback. Actual Resend Inboxes for support, payments and hello, Supabase Auth SMTP and previously issued links operate independently. The owner approves this one-time endpoint change. [Resend webhook updates](https://resend.com/docs/api-reference/webhooks/update-webhook) · [Signature verification](https://resend.com/docs/webhooks/verify-webhooks-requests)
5. Enable the runtime and stored event gates first. Check the entire current global and pinned-Topic negative preference baseline privately once signed intake is continuous. ## Pause, reconcile and resume

Pause stored dispatch, then enrollment. Preserve first-party withdrawal, private payload cleanup, incident evidence and signed restrictive intake. A local withdrawal or signed negative preference committed before irrevocable handoff prevents it. A send already in flight may arrive. Resend's raw Topic check does not guarantee a synchronous check of global marketing status. A provider opt-out whose signed event has not reached Helix can race one welcome.

Check `/api/internal/marketing/production/status` through the existing authorized production operator account when the status gate is enabled. An `unresolvedPreferenceHolds` count above zero means signed preference coverage needs reconciliation, even if no message exists yet. Keep enrollment and dispatch paused until the underlying negative evidence has been reconciled. Investigate held or failed attempts using only the necessary private evidence. A bounded retry reuses the exact prepared request and original provider idempotency key. After the safe retry window, or when evidence conflicts, preserve the unknown outcome for reconciliation. A bounce from a normal employee reply from hello does not suppress a subscriber. Ambiguous claimed marketing receipts are retained for private examination. Refresh the affected evidence and reopen controls after resolving a known interruption. [Resend idempotency](https://resend.com/docs/dashboard/emails/idempotency-keys)
