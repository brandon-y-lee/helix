# Production marketing readiness and pause boundary

Specs #538 and #595. **Held staging keeps customer enrollment and dispatch paused.** This packet is a source review record. Neither this document nor its [manifest](production-marketing-readiness.json) is consumed by runtime code or grants authority. Synthetic fixtures, green source tests, a configured environment, another service's risk acceptance and a requested release deadline do not qualify provider or production state.

The three source packages remain disabled without dedicated runtime configuration and stored controls. The existing marketing sandbox, historical consent and Auth/support permissions remain separate. Do not import old contacts, infer marketing consent from Accounts/purchases, or substitute broad credentials when a required capability is unavailable. The parent Supabase project is the approved production destination in this Spec; a restored child owns development. The hosted development-child write hold remains until the coordinating database task explicitly clears it.

Production marketing writes require the canonical customer origin and the Helix Production deployment and parent database bindings. Vercel assigns that origin to the promoted build. Consent, dispatch, event signatures and withdrawal keep their own controls. Older immutable builds retain their original database authorization reader.

## First-time welcome through Resend

The confirmation email continues to use the transactional sender. On an installed native contract, a new qualified storefront signup followed by a human confirmation creates one native welcome intent. A generation already pending at installation keeps its original sender. The raw sender cannot lease or replay native intents. A withdrawal recorded before reservation prevents the welcome. If it commits afterward, that one welcome may still arrive.

The native publisher in `workers/production-welcome/` is a separate deployment unit. Deploy its reviewed directory from an independently controlled repository and Vercel project. Its package, source access and credentials belong to that project. Storefront and Preview environments have no use for its Resend or database credential. Keep the publisher paused until the owner approves event-key custody and the complete live contract. Resend's published key types provide sending or full access. Its published sending scope excludes this event endpoint. [API keys](https://resend.com/docs/api-reference/api-keys/create-api-key) and [OAuth scopes](https://resend.com/docs/guides/building-a-resend-oauth-client).

1. Produce the public template artifact locally with `node --import tsx scripts/render-native-welcome-template.ts`. Review its subject, HTML, plain text and `contentSha256` against the published template. Its preference link uses the reserved `{{{RESEND_UNSUBSCRIBE_URL}}}` placeholder. It contains the Helix Labs LLC postal address printed in the site's Terms and Privacy Policy. Keep the HTML and text byte-exact when comparing using the artifact field order `subject, html, text`. [Resend Templates](https://resend.com/docs/api-reference/templates/create-template).
2. Qualify one active Automation for `helix.welcome.confirmed.v1`, one immediate Send Email step, the exact published template and the Helix Marketing Updates Topic. Record the effective sender, monitored Reply-To and draft/active configuration. For a new Contact with no preferences, the Topic must default to `opt_in` for the first welcome to arrive. Existing global and Topic opt-outs still take precedence. The native template's preference link opens Resend's hosted preferences. A mailbox one-click unsubscribe applies to all marketing from the Resend account. Account and support mail continue independently. [Automation trigger](https://resend.com/docs/dashboard/automations/trigger) and [Send Email preferences](https://resend.com/docs/dashboard/automations/send-email).
3. Use the reviewed worker project and production database role described below. The empty authenticated `POST /api/wake` accepts no recipient or event properties. The storefront dispatches confirmations with its dedicated transactional sending key. The independent publisher alone submits the confirmed welcome event.
4. Each wake commits at most one attempt before publishing its fixed event. A `submitted` result records Resend's matching HTTP 202. The event receipt has no run or email ID. The existing `uncertainMessages` count also includes handoffs currently in flight. Page the responsible marketing operator when a privacy-safe, authenticated count finds any `native_unknown` message, or a `native_reserved` message with `last_admitted_at` at least two minutes old. Two minutes exceeds the publisher’s eight-second dispatch window and accommodates the bounded database finish. Poll at least once per minute while dispatch is active; an overdue or failed monitor check also needs operator attention. Include the target, deployment and aggregate count only. Perform reconciliation from a read-only operator session. The local crash rehearsal exercises that exact alert and verifies that the worker makes zero additional provider requests. Reconcile a held attempt against independently bound evidence, using the nonsecret attempt ID when available. Preserve the uncertainty and its quota reservation when evidence is ambiguous. No automatic resend occurs. A single welcome can therefore be missed. Positive delivery requires a separate immutable match. [Send Event](https://resend.com/docs/api-reference/events/send-event).
   For an independently associated run, inspect the specific Automation run and its welcome step through the provider dashboard. A skipped Send Email step establishes a skipped welcome. A completed Send Email step with the qualified template, recipient and immutable email ID establishes the send; a separately verified delivery event for that same ID establishes delivery. The documented run response can have a null trigger output. A recipient, template, approximate time, completed Automation or HTTP 202 alone cannot link a run to a particular Helix attempt. In that case the operator leaves its outcome unknown. Neither the public site nor the event publisher reads the provider's message history. [Resend run and step evidence](https://resend.com/docs/dashboard/automations/runs).
5. Pause the native publisher first and enrollment next. Keep withdrawal and restrictive event ingestion operating. Resuming a compatible worker can process unreserved, unexpired native work. Returning to an older storefront cannot move a reserved or pending native welcome into the raw sender.

The earlier qualification record below still applies to original raw welcome and confirmation contracts as relevant. For new native welcomes, the independently qualified Automation owns the preference check and the fixed event publisher owns submission. Local proof is `node scripts/db/test-production-native-welcome.mjs`; it uses disposable PostgreSQL, the actual publisher, and a simulated provider, including missing Contact, both opt-outs and a lost acknowledgement.

## Ordered pause and recovery

This is a procedure for a separately authorized operator, not a command executed by this Ticket. Resolve the exact deployed project/database/provider identity and current state before each later mutation.

1. Pause **stored dispatch** and **runtime dispatch** first. Record effective state and timestamps. Pause **stored enrollment** and **runtime enrollment** separately if new requests/confirmation should stop. Neither setting retracts an already prepared or in-flight provider request: preparation is the admission point and delivery can still occur afterward.
2. Preserve capability withdrawal and its required dedicated production storage/configuration. Do not remove capability hashes, identity, quota reservations or correlation evidence. Qualified signed-event ingestion remains available independently of enrollment/dispatch so late bounce/complaint can restrict. Keep both runtime and stored event controls enabled only while the qualified route/signature/isolation contract remains sound.
3. If event routing, signing or environment isolation is suspect, coordinate with the support routing owner before any account-wide change. Use its exact continuity/disposition and rollback plan; preserve or quarantine bounded private evidence through its approved path. Do not route production events into development as a convenience. This packet supplies no hook mutation or continuity claim.
4. Status has separate runtime/stored controls. If production issuer/admin authorization is uncertain, pause visibility independently; do not fall back to another project's session, user metadata or worker caller secret. Withdrawal and safe restrictive ingestion do not depend on Operator visibility being available.
5. Reconcile read-only from normalized consent/revision, prepared identity/digests, provider binding/conflicting IDs, retained quota and event evidence. Distinguish provider acceptance, delivery summary and uncertainty. Never automatically resend, regenerate erased payload/capability/identity, clear suppression/holds, or refund unknown charges. Preserve the first provider binding. Broader provider searches require separately scoped read authority and private handling.
6. Roll back runtime deployment only to a separately reviewed schema-compatible artifact, with controls still off. Do not reverse installed schema, drop/truncate private records, reset history or clear restrictions to make an old artifact run. Exact provider changes use the support-owned rollback sequence. If compatibility or continuity cannot be established, remain paused.
7. Resume only after renewed exact identity/content/scope/budget/cleanup evidence, required source/release gates, current native permission, and separately recorded activation and recipient/send authority. A late `delivered` event, reconfirmation or new deployment cannot clear a complaint/bounce restriction or uncertainty automatically.
