# Product notification operation

This is the source contract for Spec #430, Ticket #437. It does not activate a provider, change the shared database, or send mail. Restricted hosted activation and cadence proof belong to #440 and the exact reviewed manifest. Product requests and marketing permission remain separate.

## Request and cancellation behavior

The PDP records one request for the next canonical transition to Purchasable. A request expires twelve calendar months after it was made. Existing requests retain their original creation time and consent evidence. Repeated enrollment does not extend an active request; a deliberate new request after withdrawal, expiry, or consumption creates a new generation. Replaying the original submission identity never creates that later generation.

The marketing checkbox is unchecked by default. A newly checked request supplies the reviewed marketing template contract and a new confirmation capability to the existing subscription boundary in the same transaction. If marketing admission is unavailable, neither enrollment nor confirmation is committed. Historical Product waitlist evidence never becomes a subscription. For a checked joint request with a forbidden development recipient, the public response is generic and neither portion is persisted, matching the marketing request boundary. Unchecked enrollment keeps its independent persistence behavior. Public success describes receiving the request rather than promising delivery.

Guests and Account holders use `/product-notifications` to request cancellation links by email. This remains reachable from the footer when the original Product page disappears. Recovery never returns links, request counts, or Product interests to the requesting browser. It only queues mail to the existing enrollment address under the shared recipient restrictions. There is no bare email-and-Product cancellation operation and no broader Account or marketing authority.

Each recovery email contains at most twenty separate links, each bound to one current enrollment generation. A fresh explicit request after the sixty-second cooldown selects the least recently served generations; never-served requests are ordered by request time and stable identity. This reaches requests beyond the first twenty. Existing unexpired links remain valid. Retries of the same request identity never advance selection. An outstanding or uncertain email coalesces further requests until delivery or reconciliation resolves it.

Recovery admission applies durable limits before looking up enrollments: thirty requests per hour globally, ten per trusted source, and three per normalized address across all Products. Throttled, missing, forbidden, expired, and cancelled requests receive the same public response. Each link expires within twenty-four hours and never outlives its enrollment. Opening or scanning it does nothing; explicit same-origin POST cancels only that generation. Cancellation remains available if the Product is archived, renamed, or currently Purchasable, and when new sending is disabled. A send already admitted to the provider may still arrive.

Authorization looks up a hash. The raw capability also exists in tightly private outgoing receipt/prepared content so delivery retries and subsequent requested recovery can reuse it. Do not print these bodies in logs or operator inspection. Retention must remove expired capability-bearing content while preserving generation, transition, request, and logical delivery tombstones. A narrowly held uncertain send still needs its correlation data until reconciled; content cleanup is not permission to recreate it.

## Catalog and delivery boundary

The current application publishes through `public.publish_catalog_product_draft`. The notification hook surrounds the complete V4 content publication inside its slug-aware transaction, after existing Product locks; the outer Family-before-Product order is preserved. It observes the final Product and Variant state, avoiding false transitions during Variant replacement. Failed publication rolls the event back too.

Purchasability includes public visibility (`active` and reached `published_at`), `available` Merchandising Status, and at least one nonarchived available Variant with Inventory Status `in_stock` or `low_stock`. Publication uses an explicit observation clock because the publisher sets `published_at` after transaction-start `now()`. Existing available Products establish a baseline without generating historical mail. Publication events and per-generation cursors, rather than cached PDP or search observations, determine the first eligible future transition.

A bounded materializer creates at most twenty intents per dispatch invocation. First provider admission rechecks current Purchasability, current public Product URL, generation, withdrawal, expiry, and the purpose's activation boundary. Before that first admission, a renamed Product refreshes only its public name and URL on the same intent; a concurrent rename retries rendering without consuming an attempt. Once attempted, the receipt and prepared request remain frozen. Delivery uses the existing stable idempotency key, leases, restricted recipients, and signed provider reconciliation. A stale unsubmitted recovery bundle is blocked without invalidating still-valid links; a later explicit recovery request can select current generations. An uncertain prepared message is never rebuilt to bypass that outcome.

Privileged maintenance SQL is not an automatic catalog event source. Any future inventory or 3PL writer must participate in this same publication/transition contract. Scheduled future publication is not an existing supported workflow; this Ticket adds no catalog scheduler. Former Product URLs remain unavailable under ADR 0006; frozen provider retries never rewrite their content to a different URL.

## Activation and local evidence

The disabled-by-default purposes are `product_availability` and `product_waitlist_recovery`. `read_product_notification_email_control()` inspects both without returning customers. The narrow `configure_product_notification_email(enabled, expected_updated_at)` operation compares both previously observed revisions; enabling advances their admission cutoffs so old transitions and old recovery work are not replayed. Operational apply requires the later exact reviewed manifest, including current baseline, allowed recipients, scheduler cadence, and secret references.

Migration `20260929052000_product_notifications.sql` replaces the six-argument enrollment RPC with the request-identity and atomic-consent contract. An old deployment fails closed after this migration; mixed-version intake is not an uninterrupted rollout. The #440 manifest must bind the exact migration and application SHA, sequence their deployment, and record the bounded intake-unavailability window and a checked/unchecked enrollment smoke test. Do not restore the obsolete RPC as a compatibility path around confirmed consent.

Use `HELIX_EMAIL_PRODUCT_FROM` independently of the website origin and Order/Support sender. Shared configuration retains `HELIX_EMAIL_SITE_ORIGIN`, `HELIX_EMAIL_REPLY_TO`, the exact verified owner recipient, and official simulator policy. Keep Resend link/open tracking disabled for capability emails and verify this on the actual sending identity during hosted acceptance. Missing configuration must block delivery without affecting Stripe settlement, existing inquiries, cancellation, or signed delivery reconciliation.

`pnpm email:deliveries inspect` provides sanitized delivery state. Do not reset a consumed transition, request identity, generation, or provider key to replay an old notice. A missing or stale Product notice is an inspectable delivery incident, not authorization for a historical backfill.

Local acceptance uses `node scripts/db/test-product-notification-contracts.mjs helix-spec358-pg` against a disposable synthetic PostgreSQL 17 database for publication, enrollment, recovery and admission concurrency, plus request/template/UI tests and guarded browser cases at 390×844 and 1440×900. Mocked browser requests cannot prove actual delivery. The final Spec gate runs browser acceptance; #440 records real hosted allowed-recipient delivery with the exact deployed SHA.
