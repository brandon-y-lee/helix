## Build and runtime

The Vercel build selects a target from the verified Helix project, environment and Git branch. The production lane requires `main`. Routine tools and PR CI select development. The scheduled production media job reads the parent anonymously. Next inlines a nonsecret lane marker for browser media and public clients. Hosted server clients verify the platform context independently. Configuration must use the exact project URL without credentials, custom paths or query strings.

Only publishable or legacy anon keys can be embedded in a build. For new opaque Supabase keys, independently obtain SHA-256 pins from the project's credential provisioning record before placing a key in its deployment scope. Configure `HELIX_DEVELOPMENT_SUPABASE_ANON_KEY_SHA256` or its `PRODUCTION` counterpart for an opaque public key. Generic server/operator service keys use the corresponding `SERVICE_ROLE_KEY_SHA256` pin. Existing legacy JWTs must declare the correct project and role. The provider validates the credential at request time. Enter credentials directly in their authorized secret store. Keep management tokens outside the application, and verify historical artifact access after a key is retired. A GitHub job should use only its specifically named public credential and the associated reviewed pin.

When Search is enabled, the protected `HELIX_DEVELOPMENT_ALGOLIA_APP_ID` and `HELIX_DEVELOPMENT_ALGOLIA_SEARCH_KEY_SHA256` pins come from the independently verified development app and search-only key. Production uses the same names with `PRODUCTION`. Rotate a public search credential and its reviewed fingerprint together.

The workload's actual database identity comes from `public.read_helix_environment()`. It returns a single nonsecret target/ref pair to the privileged reader. Install the bootstrap DDL, verify the hosted project independently, and have the database owner bind the singleton once before the Catalog media migration. An empty, contradictory or preexisting wrong marker blocks cutover. Ordinary release writers check the binding without creating or modifying it. The owner also enrolls an existing, separate migration login for each target after verifying its TLS endpoint, provider identity and marker row. Run the owner script through a private, already authenticated psql session using `writer_role`, `expected_environment` and `expected_project_ref` as psql variables. Its transaction grants that login execution of both marker readers, history SELECT/INSERT, and one argument-free operation for this Catalog migration. The marker table, Catalog tables, schemas and original security-definer routines stay with their existing owners. The writer can run the read-only media postflight after the migration. Before granting schema access, enrollment checks effective EXECUTE privileges, including grants inherited from PUBLIC. Unexpected access to privileged routines in the private or history schemas blocks enrollment. It also checks for newly exposed privileged API routines in the public schema. If a privilege, owner or target check fails, investigate it before preparing a new enrollment. [Owner enrollment](../../supabase/operations/release-bootstrap/enroll_catalog_media_release.sql) · [Reviewed forward migration](../../supabase/migrations/20261120131137_bind_catalog_media_to_environment.sql)

To qualify the joined migration runner in a disposable database, run `node scripts/db/test-catalog-media.mjs --container=helix-spec358-pg --environment=development --release-cli=/absolute/path/to/supabase` with Supabase CLI 2.117.0 and repeat with `--environment=production`.
