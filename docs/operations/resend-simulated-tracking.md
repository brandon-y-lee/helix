# Restricted simulated tracking

Ticket #432 / Spec #430 adds source and local verification. It performs no remote migration, account configuration, email send, label purchase, carrier request, inventory operation, or real fulfillment. Both the database `order_tracking` control and `HELIX_ORDER_SIMULATION_ENABLED` start disabled. Hosted activation and actual allowed-recipient delivery belong to the exact reviewed R1-10 manifest.

## Operator and customer experience

An active `admin` with `orders.simulate` can use `/admin/demo-orders` to look up one exact Order Number and allocate its remaining line quantities to a Simulated Shipment. Catalog roles and customers cannot use its read or mutation endpoints. The application checks the verified session, active capability, restricted development environment, same origin, and bounded request. The database rechecks the active Operator and payment authority. An Order Number identifies the lookup; it grants no customer access.

Eligible Orders are currently paid Sandbox Orders created after tracking's first database activation, with matching verified payment, sandbox account/contract and paid attempt, plus a retained post-activation confirmation intent from R1-01. The first activation cutoff is permanent across disable/re-enable. Older Orders and Orders whose source receipt content was cleaned up require a new controlled demo purchase. The original frozen recipient is reused, including an invalid/missing recipient remaining unsendable. Delivery never falls back to an Account address or redirects private content to the owner.

Partial and split allocations use existing Order Line identifiers and positive integer quantities no greater than the remaining ordered quantity. An Order lock serializes competing allocations. Accepted history is bounded to 100 events and 100 shipments per demo Order; create a fresh controlled Order for further rehearsal after this limit. No allocation is reclaimed after an exception or delivery.

The supported transitions are dispatched → in transit/delivered/exception, in transit → delivered/exception, and exception → in transit/delivered with an explicit internal resolution reason. Delivered is terminal. A stable command identifier and expected revision prevent stale/concurrent requests from recording the same transition twice. The interface keeps the exact command for retry when its outcome is uncertain. The shipment, event, allocation and applicable notice commit together, or none do.

Dispatch, delivery and exception each create one `order_tracking` notice tied to the immutable committed event. In-transit updates only affect the timeline. The email includes the demo Order, simulated shipment number, selected items and event; it explicitly states that no real charge occurred, no goods will ship, and carrier events are simulated. No street address, private receipt link, operator identity, internal resolution reason or real carrier link is included. The existing private `/checkout/success` receipt displays the same accepted tracking history after its existing ownership checks. Disabling new simulation preserves history reads. A missing optional tracking migration or temporary tracking failure does not make the paid receipt fail.

## Refund and delivery ordering

After the existing Stripe verifier establishes a successful full refund, the existing payment-contract read identifies whether tracking's schema is installed. Its new `trackingSchemaVersion: 1` projection requires a monotonic private simulation freeze before rewards/referral reconciliation. The marker changes neither immutable accepted terms nor financial facts. This observation is independent of Resend credentials, configuration and availability. Replayed observations are harmless; refunded status and existing verified refund evidence also block simulation.

Source can deploy before the separately approved tracking migration. A successfully validated legacy payment contract without the marker, or a successful null contract result, preserves existing refund reconciliation. Such Orders cannot later qualify for tracking: the first activation cutoff is established by the database clock after migration, and contracts cannot be added to an already paid Order. Read errors, malformed contracts and unknown marker versions fail closed; there is no missing-function fallback for refunds. Once the marker is present, failure to record the freeze leaves reconciliation retryable without claiming completion, even when new simulation is disabled.

The guarantee begins when the verified refund observation commits locally. Stripe's remote action and local observation cannot be atomic. Provider-event retries handle failures to record that observation. A verified refund exception also preserves this freeze even if a later failed provider check records an unknown refund status.

Mutation and tracking preparation lock the Order before shipment/intent records. A committed freeze prevents all later tracking transitions and preparation attempts, including retries. A provider request prepared before the freeze may already be in flight and cannot be recalled. Its signed callbacks still reconcile accepted history. No database transaction stays open across a provider request. Unattempted or retryable notices blocked by the freeze retain their logical identity; retrying cannot override the freeze or reset the provider window.

The normal dispatcher, restricted-recipient policy, frozen payload, stable provider key, five-attempt/23-hour cutoff and signed callback handling from [Order confirmations](./resend-order-confirmation.md) apply. Sender validation is per purpose; confirmation and tracking share `HELIX_EMAIL_ORDER_FROM`. Prepared requests keep their original sender and content. Common transport configuration and the Order sender's readiness are reported separately by `pnpm email:deliveries inspect`.

## Activation and rollback contract for R1-10

The manifest must include the exact reviewed SHA, non-production database and Stripe sandbox identity, approved Helix origin, Resend sender and callbacks, allowed recipients, dispatcher cadence, and both simulation switches. `read_simulated_tracking_control()` is read-only; `configure_simulated_tracking(enabled, expected_updated_at)` changes only the exact inspected database revision. Its first enable fixes the permanent Order creation cutoff; later toggles preserve it. This Ticket never calls the remote configuration function. Enabling the application flag alone cannot create events while the database admission control is disabled. Next.js production build mode is not evidence of live commerce; actual live Stripe configuration is rejected.

The `dev` deployment may publish the reviewed source while tracking remains inactive, before the separate R1-10 migration apply. Activation requires both the reviewed migration and matching source, followed by the approved database and application controls. Then create fresh controlled guest and account Stripe Sandbox Orders and prove one confirmation plus tracking on each same Order with local listeners stopped. Simulate partial/split dispatch, in transit, exception/resolution and delivery; verify notice counts, recipient, template facts, private receipt and actual mailbox receipt separately from provider simulator events. Rehearse repeated/stale commands, concurrent remaining quantities, wrong customer/catalog role, forbidden live configuration, provider outage and blocked recipients. Record sanitized identities, timestamps, deployed SHA and outcomes only.

Exercise a verified full sandbox refund during simulation and email preparation, including a failed ancillary refund effect. Prove the freeze remains, later transitions/preparations stop, already prepared delivery callbacks are retained, and existing financial accounting still reconciles on retry. Disable database admission and the application flag to stop new simulation; disable the independent email dispatcher to stop new outbound invocations. In-flight prepared requests may complete. Preserve webhook verification and all existing financial event processing. Rollback never deletes events, allocations, message identities or historical Orders.

It covers real concurrent allocation and transition races, refund ordering and first/retry preparation, installation/activation against a legacy contract reader, permanent activation cutoff, atomic transition/intent rollback, private grants/RLS, terminal states and retained identities, alongside the existing payment-contract and confirmation assertions. Unit tests exercise the HTTP/private-receipt and email boundaries. The verification-only browser routes contain synthetic data and never authorize real writes; mobile/desktop browser evidence and hosted provider proof remain separate from these unit tests.
