# Disabled production support source package

Tickets #528–529 / Spec #527, outcome #524. This directory is deliberately **outside** `supabase/migrations`. Nothing discovers, installs or activates it automatically. It contains no operational target identity, secrets, networking, polling/cron, storage grants or customer-send mechanism.

## Installation boundary

`install.sql` is a single transaction intended for a trusted owner/operator with BYPASSRLS. It refuses to replace an existing private schema. The future operator must first obtain action-specific installation approval, independently verify the exact selected production project and effective development-access cutover, inspect grants/default privileges and the reviewed source, and use the separately approved installation procedure. Do not run ordinary dev migration discovery against this package. No hosted installation was performed for this Ticket.

The singleton contract has null project/contract identity, zero capacity/quotas and five false controls: admission, worker, full-media qualification, isolation qualification and operations qualification. Source includes no setter RPC or operational identity values. Future operator configuration is a distinct approved action. These flags are operator attestations, not independent evidence of actual storage, provider, custodian, access isolation or operational readiness. Full-media and operational qualification remain mandatory; no text-only release is permitted. Admission can pause independently of draining owned work. Signed owned callbacks can reconcile even while admission and worker are off.

`legacy-alias-resolver.sql` is a **separate** manual-only installation on the separately verified legacy reconciliation target, after appropriate approval. It does not install the production schema and `install.sql` does not install it. It only checks opaque SHA256 digests against all exact normalized stored legacy reply aliases. It does not read provider bodies or fetch attachments. A missing/incompatible/inaccessible legacy relation raises the bounded `support_legacy_aliases_unavailable` error (SQLSTATE55000), so callers return retryable failure rather than acknowledge away pending legacy obligations. An existing readable relation with no matching aliases definitively returns false. Missing RPC, timeout or malformed RPC response are likewise operational uncertainty, not an unmatched verdict.

## Data and RPC boundary

`support_production_private` is non-exposed. Every table forces RLS. PUBLIC, anon, authenticated and service_role have no direct schema/table/function privileges, even when service_role has BYPASSRLS. Public SECURITY DEFINER functions use `search_path=pg_catalog`; only service_role gets EXECUTE. Trusted owners/operators remain trusted. No generic support, commerce or email-intent tables are reused.

- `read_support_prod_contract()` returns `{projectRef,contractId,admissionEnabled,workerEnabled,fullMediaQualified,isolationQualified,operationsQualified}`.
- Other production functions take a single `p_input jsonb`. All require `projectRef` and `contractId` matching the stored contract. Unknown keys fail closed.
- `submit_support_prod_inquiry`: additionally `submissionId,payloadHash,capabilityHash,sourceHash,emailHash,name,email,inquiryType,subject,body,photos`. Photos are ordered `{uploadId,contentType,byteSize}` declarations. It returns stable `{inquiryId,submissionId,status:"saved",outboxId,photoStatus:"declared",reservedBytes}`. Exact canonical text/manifest, supplied payload hash and capability hash are all compared on retry. Source changes do not charge a retry again.
- `claim_support_prod_outbox`: additionally `leaseId` (fresh UUID on every claim) and `leaseSeconds` (30–120), returning one `{outboxId,leaseId}` or null. Lease IDs cannot be reused.
- `start_support_prod_send`: additionally `outboxId,leaseId`, returning `{outboxId,requestText,requestHash,idempotencyKey,attemptCount,firstAttemptAt}` or null. It commits the permanent first-attempt marker before the caller can perform its bounded provider call. A lease can prepare once.
- `complete_support_prod_send`: additionally `outboxId,leaseId,outcome` (`accepted`, `unknown`, `rejected`) and `providerEmailId` UUID only for acceptance; returns a fenced boolean. Rejected work is held for reconciliation, not rekeyed.
- `record_support_prod_sent`: additionally `outboxId,deliveryToken,providerEmailId,messageId,from,to,eventId`, returning `matched`, `duplicate`, `conflict` or `unmatched`. The caller must verify the signed provider event first. Matching requires an already-owned first attempt, exact token/envelope and immutable provider UUID/RFC Message-ID. Callback correlation remains available when paused and after the automatic retry window.
- Separate legacy RPC: `support_legacy_reply_aliases_match(p_address_hashes text[]) -> boolean`. Requires a nonempty one-dimensional array of at most 100 lowercase64hex digests. Every digest must match a stored exact normalized alias. No domain/prefix inference. Only a successful readable lookup can establish definitive false for unknown aliases; unavailable target state must remain retryable.

The outbox freezes JSON text, its SHA256 and `support-primary:<outbox UUID>` idempotency key at admission. All retries use these exact serialized bytes/key. From is `Helix Website <contact@helixskin.us>`, To is only `support@helixskin.us`, visitor is Reply-To only, subject is `Helix Website inquiry <outbox UUID>`. Visitor subject/message appear only in plain text. A fixed plain-text warning states that visitor-provided identity and Reply-To are unverified and must not justify disclosure of Account, Order or private information. Provider REST tags are the opaque outbox ID, contract ID and unguessable64hex per-outbox delivery token (`helix_support_outbox`, `helix_support_contract`, `helix_support_delivery`). Do not log requests, text, token or private event payloads.

The first-attempt horizon is 20 hours, before provider24-hour idempotency expiry. Unknown work retries only the same frozen body/key before that horizon, then remains held for reconciliation. Provider acceptance or an `email.sent` callback is **not** proof of native Inbox arrival. Provider UUID and actual RFC Message-ID are separate immutable fields. Each worker claim reconciles at most20 expired rows, selected oldest-first with `FOR UPDATE SKIP LOCKED`, then independently claims at most1 eligible job. A locked expired row cannot block useful eligible work and remains available to a later invocation. Partial active-work indexes order due work by `(next_attempt_at,created_at,id)` and expired attempts by `(first_attempt_at,id)`; no unbounded expired-row UPDATE or queue-wide lock is used. No customer send, auto-ack, reply, forwarding, AI or CC/BCC exists here. The optional manual `media.sql` extension adds separately frozen internal media work, described below.

## Capacity and preservation

Admission serializes the identity, three independent hourly source/email/global limits, capacity reservation, validated text/manifest and primary outbox in one transaction. Default limits are zero. Production thresholds require separate operational approval. Each declared slot reserves 14 MiB (10 MiB raw + 4 MiB clean), even for one declared byte: max five slots reserve70 MiB although accepted original aggregate remains20 MiB. No upload is minted or object accepted in T1. No capacity release, record deletion, cleanup or retention routine is provided. Originals/unassessed records stay preservation-held by default; future media/assessment work must preserve this boundary.

## Local proof

Run `node scripts/db/test-production-support-contracts.mjs`. It uses only the existing running `helix-spec358-pg` container, verifies label `helix.task=spec358-synthetic-sql`, exact image `public.ecr.aws/supabase/postgres:17.6.1.159` and PostgreSQL17, and creates/drops one uniquely owned database. It never starts/removes the container, changes shared roles/security, reads credentials or calls a provider. Synthetic fixtures configure identity/controls only inside that database. Concurrent proofs observe a second actual connection blocked on the admission lock before releasing the first transaction. Provider mutations stay zero. This is local contract proof, not production readiness or qualification.

## Provider boundary remains unqualified

A new production callback does not stop an old account-wide subscription delivering production envelope or delivery-token metadata to a development endpoint. Ignoring that data in application persistence does not prevent arrival. The per-outbox token and database isolation are not substitutes for qualified provider subscription, credential and developer-tool boundaries. Before activation, verify the complete current inventory and effective scopes, preserve legacy callback/reply obligations, and prove no production support metadata can reach an unapproved development destination. A label or assumed sender/key filter is not provider-enforcement proof. This describes a prospective qualification requirement, not a claim of current customer exposure.

Readiness negative cases must include an enabled account-wide development subscription alongside a new production subscription, receiving/Inbox metadata, incomplete/unknown scope, retained development send/read/manage authority, and pending legacy obligations without isolated reconciliation. Under separately approved synthetic canaries, verify actual intended operator receipt and absence of matching metadata in development requests/logs/queues. Local assertion packets cannot establish actual provider state or authorize activation.

## Manual T2 extension

`media.sql` is a separately reviewed single transaction installed only after `install.sql` under a separately authorized exact-target procedure. It does not create Storage resources, configure a scheduler, provide credentials or enable any gate. It adds a null `photo_bucket` and zero `photo_worker_limit` (bounded to 16 active processing leases), returned by `read_support_prod_contract` as `photoBucket` and `photoWorkerLimit`. Every new table forces RLS and denies direct application-role access. New public RPCs remain service-role-only, fixed-search-path, strict-input boundaries.

Immutable slots are seeded from the canonical manifest, including existing T1 declarations, without charging the already reserved 14 MiB per slot again. Capability-bound `reserve_support_prod_photo`, `complete_support_prod_photo` and `read_support_prod_photos` do not trust browser completion as byte acceptance. Mint attempts and a conservative two-hour ceiling are persisted before Storage signing. Claim/record/finish RPCs fence one original at a time, preserve raw hashes and independently serialize actual accepted originals at 20 MiB per inquiry. Exhausted work is held. There is no raw/clean deletion or reservation-release RPC; expiry and absence are not proof that a late PUT cannot recreate an object.

`prepare_support_prod_media` freezes ready, previously unassigned photos in manifest order with the verified primary RFC parent and subject. `finalize_support_prod_media` freezes the version-pinned serializer hash and byte count before inserting sendable work. It stores metadata only, not Base64. Media reuses shared outbox leases, permanent first-attempt horizon, callback correlation and globally unique provider/RFC identities. The primary request bytes stay unchanged; repeated inquiry lookup explicitly selects the primary. Reconstruction mismatch goes to `reconcile_support_prod_media` before any provider attempt. Missing parent holds media; late photos get distinct immutable batches, never a changed prior request. Actual native grouping remains a canary requirement.

Run `node scripts/db/test-production-support-media.mjs` as well as the T1 proof. Both verify the existing labeled PostgreSQL17 container and create/drop only uniquely owned synthetic databases, without shared-role/container changes or provider calls. The T2 proof covers existing-declaration extension, actual overlapping mint/completion/processing/fleet/aggregate/batch/finalization races, stale leases, private role denial, expiry/exhaustion, rollback, preservation, immutable unknown retries and maximum per-file Base64 padding. It does not prove actual Storage finality, hosted decoder memory, provider delivery, Inbox access or archive restoration.
