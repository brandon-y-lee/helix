## Retained raw delivery and confirmation

`POST /api/internal/marketing/production/dispatch` processes at most one intent. Independent `HELIX_PRODUCTION_MARKETING_WORKER_TOKEN` authorization precedes cleanup, claims, quota and provider work. GET/HEAD have no handler and cannot dispatch. Public responses contain only idle/deferred/accepted/uncertain/unavailable status. Provider acceptance is not mailbox delivery.

Both dedicated runtime `HELIX_PRODUCTION_MARKETING_DISPATCH_ENABLED=true` and stored dispatch control/configuration are required. Fresh dispatch remains false, contract absent, daily/monthly allocation zero. Existing production origin/project/deployment/Supabase binding remains required; no generic environment fallback. Configuration assertions are not proof of effective provider or database isolation.

`HELIX_PRODUCTION_MARKETING_DELIVERY_CONTRACT` is an exact JSON string with six fields: version `production_welcome_delivery_v1`, plain approved `from`, `replyTo`, exact `topicId`, approved `postalAddress`, and `templateHash` equal to the server export in `lib/production-marketing/templates.ts`. The SHA256 of its exact UTF-8 bytes must match the stored contract text. HTML/text structure and frozen copy are included in the local source hash. Changing template/contract is a new review/qualification action; retries never re-render. This Ticket supplies no actual approved sender, postal address or Topic values.

Sending uses only `HELIX_PRODUCTION_MARKETING_PROVIDER_KEY`. Welcome requires independently qualified `HELIX_PRODUCTION_MARKETING_PREFERENCE_KEY` and current native Contact/global/Topic allowance; missing Contact, missing/unknown Topic, denial or failed read defers before preparation. It never creates/imports Contacts or overwrites permission. Sending credentials are not reused for preference or template reads. No provider templates are fetched. Real least-privilege scope/custody remains an operational gate; no broader key is created as a fallback. Acceptance of another service's credential risk supplies no marketing approval.

Confirmation decrypts only its original authenticated C1 envelope and compares the full immutable binding and both capability hashes. Current key configuration remains supported. Retained IDs may resolve only through the explicit server-only `HELIX_PRODUCTION_MARKETING_CAPABILITY_KEYS` JSON map of ID to 64-hex key; no filename, URL or provider lookup. Rotation/custody is not performed here.

## Admission, retries and retention

Only a successful explicit confirmation transaction admits one held welcome per normalized address/generation/purpose. Repeated or concurrent confirmation cannot create another. No historical confirmed-generation backfill, account/purchase trigger, campaign scheduler, offer or lifecycle behavior is added. Held welcome is not send permission.

First promotional preparation also enforces the selected per-address rolling limits: one promotion per 24 hours and three distinct promotions per seven days across consent generations. The existing address lock serializes the check with preparations and retries before budget reservation. Each prepared logical promotion counts using its latest handoff admission, including uncertain or later-cancelled messages and erased payloads. A same-identity retry refreshes that admission without taking a second slot. Confirmation mail stays independent. Capped welcome remains held for the existing defer and expiry rules; no clock is extended. This fresh manual package includes the safeguard from Ticket #548 and is not an upgrade script for a previously installed package.

Claims use a 60-second fenced lease. Address lock precedes message lock, followed by the shared quota lock. Preparation rechecks current consent/revision, local suppression, stored dispatch and exact contract, then freezes exact JSON wire bytes, metadata, headers and idempotency identity while reserving UTC day/month allocation atomically. No transaction spans provider I/O. Preparation is the first handoff linearization point: prior withdrawal blocks it; a first prepared request may still start after withdrawal. Later retries require fresh native allowance and durable eligibility/quota admission and cannot restart after withdrawal.

Known provider uncertainty persisted by `finish` may retry the same bytes/key within 23 hours of first preparation. Charges remain reserved, with unique message/period entries. A later UTC day/month needs its own current allocation while retaining earlier entries. Admission time is captured after the quota lock, and a worker paused across a UTC date boundary holds before handoff. Requests still have bounded network deadlines; the system does not promise a provider arrival time or perfect synchronization with provider billing clocks. Shared-account capacity and other producers' usage require separate qualification.

Unknown preparation/finish persistence gets no automatic replay. A prepared row with an expired lease is deliberately not reclaimed. Read-only reconciliation is required; a lost finish response after an actual accepted commit also cannot create a new send. Conflicting provider identity is held; first binding is never overwritten. P3 consumes this seam in source; no event receiver is installed or routed.

Confirmation payload expiry is the original request expiry; preparation does not restart its 24-hour clock. Welcome payload expiry is first preparation +24 hours. The source envelope is cleared after confirmation preparation, and consumed/withdrawn/superseded held input retains P1 erasure behavior. Every prepared body copy is erased at its due deadline by the narrow idempotent cleanup operation, regardless of accepted/cancelled/prepared/uncertain state. Digests, immutable identity, sender/recipient correlation, provider binding, restriction hashes, accounting and uncertainty holds remain. Erased bodies cannot be reconstructed or automatically retried. Delivered withdrawal capabilities still restrict via their retained hashes.

The worker runs cleanup before claims, but there is no scheduler in this Ticket. Due bodies are ineligible even before physical erasure. A qualified periodic cleanup cadence must exist before activation; source alone makes no exact-time physical-erasure claim. No historical/hosted records are cleaned by this work.

## Signed events and private status

P3 adds `POST /api/webhooks/marketing-production`. It requires dedicated `HELIX_PRODUCTION_MARKETING_EVENTS_ENABLED=true`, a separately provisioned `HELIX_PRODUCTION_MARKETING_WEBHOOK_SECRET` (never generic `RESEND_WEBHOOK_SECRET`), the existing production deployment/database binding, and stored `events_enabled=true`. Both controls default off. No send key is required. Exact raw bytes are bounded to 128 KiB and a three-second read deadline, then verified locally with the Resend SDK and fresh bounded Svix headers. No raw event, address, subject or capability is copied into the normalized event journal.

The retained raw-delivery path correlates prepared P2 identities using exact production tags, message UUID, provider UUID, purpose, frozen sender and one recipient, plus retained preparation/digest proof. Unknown, unprepared, sandbox or altered identity cannot create subscribers or delivery messages. Exact normalized duplicate event IDs are idempotent; changed reuse rejects. Event-ID lock precedes address/message/provider-ID locks. First provider binding never changes; conflicting event and response IDs are retained as normalized evidence and require reconciliation. Callbacks arriving before a live response leave it finishable; same-ID acceptance completes. Either ordering of signed callback and known uncertainty holds against automatic retries. Due payload erasure does not erase restrictive correlation proof.

Stored events remain available while enrollment or dispatch is paused. Bounce, complaint and suppression are monotonic subscriber restrictions; complaint outranks bounce, which outranks suppression. Failed/delayed events remain separate from local suppression. All events remain in the journal; the deterministic delivery summary orders pending, sent, delayed, delivered, failed, suppressed. Provider acceptance and delivery status are separate axes; a later `sent` cannot restore or downgrade restriction. This summary does not claim mailbox receipt or offer reconciliation actions.

`GET /api/internal/marketing/production/status` requires dedicated `HELIX_PRODUCTION_MARKETING_STATUS_ENABLED=true` and stored `status_enabled=true`. It binds `NEXT_PUBLIC_SUPABASE_URL` to the exact production parent before calling the existing server-verified `getCurrentUser` path, then supplies only that verified actor UUID to the narrow service RPC. The RPC requires canonical active `public.admin_memberships` role `admin`; user metadata, caller-supplied actors and worker tokens confer no authority. The response is private/no-store and contains exactly eleven finite nonnegative counts, including prepared, accepted, delivered, failed, suppressed and uncertain messages. No membership is provisioned by this package.

Run `node scripts/db/test-production-marketing-delivery.mjs --events` for the owned networkless P3 database proof. It runs the existing P1/P2 SQL/worker proofs with the P3 finish replacement, plus real SDK-signed receiver/storage/status adapters against PostgreSQL, duplicate-ID and provider-ID contention, both callback/response lock orderings, old-generation suppression versus new preparation, erased-body correlation, grants and RLS. Only provider HTTP is synthetic. No database URL/container override is accepted. Ordinary focused checks are `pnpm exec vitest run tests/production-marketing-events.test.ts`.
